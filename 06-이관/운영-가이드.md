# 운영 가이드 — 콘텐츠를 고치고 발행하는 방법

| | |
|---|---|
| 작성일 | 2026-08-20 (목) |
| 근거 | PRD **NFR-18** · §7.3 상태 머신 · D1 · FR-P07-04 |
| 대상 | 사이트를 넘겨받아 운영하는 사람 |

> **지금 이 사이트의 콘텐츠는 전부 코드 안의 정적 데이터다.** 관리자 화면(`/admin`)은
> 7화면이 다 그려져 있지만 **저장되지 않는 목업**이고, 화면 위에 그 사실이 띠로 붙어 있다.
> 이 문서는 두 시기를 나눠서 쓴다 — **지금(정적 데이터)** 과 **어드민이 붙은 뒤**.

## 1. 지금 — 콘텐츠를 고치는 곳

전부 `05-서비스-nextjs/app/` 안의 파일 하나씩이다. 같은 내용이 두 곳에 있지 않도록
**목록·상세·홈이 전부 같은 파일을 본다.** 한 곳만 고치면 세 화면이 같이 바뀐다.

| 무엇 | 파일 | 화면 |
|---|---|---|
| Work 프로젝트 | `app/_works.ts` | 홈 S6 · `/work` · `/work/[slug]` |
| Insight 아티클 | `app/_insights.ts` | 홈 S7 · `/insight` · `/insight/[slug]` |
| 빌더 프로필 | `app/_builders.ts` | 홈 · `/builder` · Work 상세 참여자 |
| FAQ | `app/_faq.ts` | 홈 S9 프리뷰 · `/faq` |
| 유튜브 영상 | `app/content/view.tsx` 의 `VIDEOS` · `FEATURED` | `/content` |

> **FAQ 와 영상에 관리 화면이 없는 것은 실수가 아니라 결정이다.** PRD D1 · FR-P07-04 —
> 1차 화면 수를 17로 유지하려고 정적 데이터로 뒀다. FAQ 문항이 20개를 넘거나 영상 갱신이
> 잦아지면 그때 관리 화면을 만든다(백로그 §3-4 · §3-11).

### 고치고 반영하는 절차

```bash
cd 05-서비스-nextjs
# 1) 파일을 고친다
# 2) 화면으로 확인한다
npm run dev            # http://localhost:3000
# 3) 검증 게이트 — 실패하면 배포하지 않는다
cd .. && npm run verify
# 4) 커밋 · 푸시하면 Vercel 이 자동 배포한다
git add -A && git commit -m "content: <무엇을 바꿨는지>" && git push
```

**반영은 "즉시"가 아니라 "빌드가 끝나면"이다** (NFR-05 — 60초 이내로 안내). 정적 생성이라
배포가 끝나야 바뀐다. 배포 상태는 Vercel 대시보드에서 본다.

### 새 Work 한 건을 추가하는 예

`app/_works.ts` 의 `WORKS` 배열에 항목을 하나 더한다. 필드는 타입이 강제하므로 빠뜨리면
`npm run verify` 가 잡아낸다.

```ts
{
  slug: '커머스-리빙-리뉴얼',        // ⚠ 주소가 된다. 규칙은 아래 §3
  title: 'iloom — 리빙 커머스 리뉴얼',
  cat: 'commerce',                   // 목록 필터 키
  tag: 'Commerce', year: '2026',
  summary: '한 문장 요약. 카드와 검색 결과 설명에 그대로 쓰인다.',
  cover: 'work-iloom.png',           // public/assets/img/ 안의 파일명
  coverAlt: 'iloom 리빙 커머스 화면', // 대체 텍스트 — 비우지 않는다 (NFR-07)
  withPartner: true,
  builders: ['josh', 'minseo'],      // _builders.ts 의 슬러그. 첫 번째가 리드
}
```

추가하면 **사이트맵과 llms.txt 에도 자동으로 실린다.** 따로 손댈 곳이 없다.

## 2. 어드민이 붙은 뒤 — 발행 · 승인

상태 머신은 PRD §7.3 이고, `/admin` 목업이 이미 그 흐름대로 그려져 있다.

```
초안(draft) ──제출──▶ 승인대기(pending) ──승인──▶ 발행(published) ──내림──▶ 보관(archived)
   ▲                        │
   └────반려 + 사유─────────┘
```

| 규칙 | 이유 |
|---|---|
| **발행은 관리자만** | 빌더는 `draft ↔ pending` 까지. 홈이 "공개 전에 무엇을 확인하는지 정해져 있는가"를 외주사 판별 기준으로 걸어놓고 우리 어드민이 안 지키면 그 자체가 모순이다 |
| **반려에는 사유가 필수** | 사유 없는 반려는 "안 됨"만 전달한다. 무엇을 고쳐야 하는지 없으면 다시 올라오는 것도 같은 상태다 |
| **`pending` 은 작성자가 편집할 수 없다** | 검수 중에 원본이 바뀌면 승인한 것과 공개된 것이 달라진다 |
| **`archived` 는 404 가 아니라 301** | 색인과 공유 링크를 버리지 않는다 |
| 계정 회수 시 **콘텐츠는 남는다** | 지우면 그 사람이 쓴 글의 작성자가 사라지고 빌더 연결이 끊긴다 |

**권한이 없는 버튼은 회색으로 두지 않고 아예 두지 않는다.** 누를 수 없는 버튼은
"권한이 없다"가 아니라 "고장났다"로 읽힌다.

## 3. 슬러그 규칙 — 🔴 한 번 정하면 바꾸지 않는다

주소가 곧 슬러그다. 바꾸면 **공유된 링크와 GA4 이력이 함께 끊긴다.**

| 종류 | 규칙 | 예 |
|---|---|---|
| Work | `업종·기술 + 프로젝트명`, 한글 자연어. **고객사명 제외** (§14 Q7 — NDA·공개 동의 확인 전) | `커머스-리빙-리뉴얼` |
| Insight | `핵심 키워드 조합` | `바이브코딩-외주-고르는법` |
| 금지 | 프로젝트명 단독 (검색되지 않는다) · 고객사명 (동의 확인 전) | |

**꼭 바꿔야 한다면 301 을 함께 넣는다.** 지금은 `05-서비스-nextjs/next.config.mjs` 의
`redirects()` 에 한 줄 추가하고, 어드민이 붙으면 `redirects` 테이블이 그 역할을 한다(SR-06).

```js
{ source: '/work/옛-슬러그', destination: '/work/새-슬러그', statusCode: 301 },
```

## 4. 콘텐츠 품질 — 인계 시 명기 사항

> ⚠️ **테크니컬 세팅이 완벽해도 콘텐츠를 AI로 딸깍해서 계속 쓰면 결국 저품질로 떨어진다.**

클라이언트가 1차 미팅에서 직접 덧붙인 경고이고, PRD §9 이 "인계 문서에 명기할 것"으로
요구한 문장이다. 이 사이트가 파는 메시지가 *"AI로 만든 티가 나지 않게, 순서를 지켜서"* 라서
운영 콘텐츠가 그 반대로 가면 사이트 전체가 자기 주장을 반박한다.

사이트에 쓰지 않기로 한 것 (README §절대 규칙):

- 검증 불가 수치 (`만족도 100%` 류)
- 가격·저렴함 소구
- 실 고객이 없는 상태의 후기
- 발주자에게 의미 없는 기술 스택 로고 나열

## 5. 문제가 생겼을 때

| 증상 | 먼저 볼 곳 |
|---|---|
| 문의 버튼을 눌러도 아무 일이 없다 | `NEXT_PUBLIC_PLUUG_FORM_URL` 이 비었는지. 비면 링크가 죽는다 |
| 채널톡이 안 뜬다 | 플러그인 키가 아니라 **허용 도메인**을 먼저 본다. 키가 맞아도 도메인 미등록이면 `/boot` 가 401 로 조용히 실패한다 |
| GA4 에 아무것도 안 잡힌다 | `NEXT_PUBLIC_GA_ID` 가 비면 gtag.js 자체를 싣지 않는다 → `06-이관/GA4-세팅-가이드.md` |
| 공유 카드가 이상하다 | `NEXT_PUBLIC_SITE_URL` 이 실도메인인지. 비면 Vercel 주소를 쓴다 |
| 없는 주소인데 500 이 난다 | 한글 슬러그 이슈다. `dynamicParams=false` 를 켜지 않았는지 확인 (`work/[slug]/page.tsx` 주석) |
| 빌드가 깨졌다 | `npm run verify` 출력을 그대로 읽는다. 타입 오류면 데이터 필드를 빠뜨린 것이다 |
